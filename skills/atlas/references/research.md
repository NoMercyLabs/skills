# Research: read the whole system before writing

## Operating boundary: investigate read-only, write only docs

Investigation must not change the project. The user is handing over a working codebase and expects it back untouched.

**Only two kinds of writes are allowed:** the backup of existing documentation, and the new documentation files themselves. Nothing else, no formatting, no dependency installs, no lockfile updates.

**One deliberate exception: a bug the documentation work reveals gets FIXED, not written up.** If a documented option is never read, a binding never fires, or a method silently no-ops, the fix belongs in the code. Writing "note: this does not currently work" ships a disclaimer where a fix was possible, and the next reader inherits both the bug and the excuse. Fix it, add a regression test, prove the test fails without the fix, and say so when reporting.

**A comment proven wrong is fixed in the source, not merely avoided on the page.** Two rows of one page turned out to be a verbatim transcription of a docblock whose first two lines the code did not support. Writing the page correctly and leaving the comment standing fixes this page and nothing else: the comment is what the next writer, and every reader of the source, will believe. It is a documentation defect that happens to live in a source file, so it falls inside this exception rather than outside it.

The judgment line: fix what the documentation work uncovered about behavior the docs describe. Do not wander into unrelated refactors, formatting passes, or dependency work.

**A section that will not simplify is often reporting a defect.** When a passage keeps growing, two settings for one outcome, a caveat that needs its own caveat, an order of operations that has to be spelled out because nothing enforces it, the difficulty usually belongs to the design rather than the prose. Documentation is where that surfaces first, because writing it is the first time anyone states the whole thing to someone who does not already know it.

The clearest signal is duplicated configuration: a value the reader must set in two places for one result. That is nearly always a missing default, where one layer should read from the other and does not. Fix the code so the value is set once at the level that serves every consumer of it, and the paragraph collapses to a line on its own. Writing the careful explanation instead ships the defect to every reader and makes the library look more complicated than it is.

Within that second category there is full freedom. The new documentation is your own working product, so revise it as much as the work requires: rewrite sections, split a file that grew too large, merge two that overlap, rename, reorder, or delete a page that turned out to be empty. Expect to do this, the Phase 7 and 8 reviews exist precisely to find problems, and finding one is only useful if you then fix it. The same applies to follow-up requests: when the user asks for a change after delivery, edit the documents directly rather than starting over.

One exception worth recognizing: documentation generated by an earlier run is no longer purely yours, because someone may have corrected or extended it since. Treat anything from a previous session as existing documentation, audit it and back it up first (Phase 4). Only what you wrote in the current session is yours to change without ceremony.

When running commands to verify claims, prefer ones that only report. Safe in almost every project: version and help flags, dependency listings, `git log`/`git status`/`git remote -v`, type checks, linters in check-only mode, dry-run flags, reading build config.

Treat as unsafe unless the user explicitly approves: anything that installs or updates packages, database migrations, code formatters writing in place, `git` commands that change state, build steps that overwrite generated assets, deploy scripts, and test suites that touch a real database or external service. Test suites are worth running when they are self-contained, because a passing suite tells you a lot about whether documented behavior is real, but read the test config first to check what it touches.

When unsure whether a command mutates something, don't run it. State in the docs how something is *documented* to work versus what was *verified*, rather than guessing.

## Phase 1: Map the terrain

Build a picture of scale and shape before reading any source in depth. Cheap commands, big payoff:

- Directory tree, excluding dependency and build directories (`node_modules`, `.git`, `venv`, `Library`, `build`, `dist`, `target`, `bin`, `obj`)
- File counts by extension, and the largest source files
- Every manifest and config: `package.json`, `pyproject.toml`, `go.mod`, `Cargo.toml`, `pom.xml`, `*.csproj`, `ProjectSettings/`, `Dockerfile`, `docker-compose.yml`, CI workflows, `.env.example`
- Existing documentation anywhere in the tree, including `docs/`, wikis, and `README` files in subdirectories
- Recent `git log`, where has work actually been happening, and what does the commit history reveal about the project's direction

This tells you the project type, the size class, and where the substance lives. Read `project-types.md` in this directory for what to look for in specific ecosystems once you know what you're dealing with.

## Phase 2: Read it as one system

Now read for real. The goal is not coverage of files; it is a mental model you could defend under questioning.

Work from the outside in, following execution rather than the alphabet:

1. **Entry points.** `main`, server bootstrap, CLI command registration, scene loaders, the package's public exports. Everything else exists to serve these.
2. **Trace at least two complete paths end to end.** For a web app, a request from route to response including auth, validation, and persistence. For a game, what happens between input and visible effect. For a library, the most common call from public API down to where the real work happens. These traces are what turn a parts list into an explanation.
3. **The data.** Schemas, models, migrations, save formats, serialized assets. Where state lives and who is allowed to change it.
4. **The seams.** External services, queues, environment variables, feature flags, generated code, plugin boundaries. These are where readers get stuck and where documentation is worth the most.
5. **The deliberate decisions.** Unusual patterns, wrappers around standard libraries, hand-rolled implementations of common things. Some of these are load-bearing and expensive to rediscover. Look at tests and commit messages to distinguish deliberate design from accident.

Keep working notes as you go, an inventory of components with what each one does, and an open-questions list for anything that stays unclear. Those open questions matter: they mark the places where invention would be tempting later.

### Cover 100% of the source, and say the fraction

The standard is every non-test source file, not a representative sample. Partial reading is how a wrong default, a dead option or a binding that never fires survives: the one file nobody opened is exactly where it hides.

On a large codebase, one pass cannot hold it all. Slice it and fan out:

1. Count the files first, and count them by subtraction. The denominator is every file under the source roots minus the ones deliberately excluded, build output, dependencies, binaries, tests. Never build it from a list of extensions you expect to find: an allow-list makes every language nobody thought of invisible, and the file that disappears that way looks exactly like a file that was read and found uninteresting. `scripts/check_docs.py coverage` counts it this way, so an unfamiliar file type surfaces as unread rather than as covered.
2. Cut the tree into slices along subsystem lines, sized so one agent can read a slice in full. Twenty to fifty slices is normal for a few hundred files.
3. Name each slice by directory and let the agent enumerate its own files. Handing an agent the files to read writes the hole in advance, because whatever is missing from that list is never opened and nothing afterwards can tell. Naming paths to skip is fine; naming the paths to read is not.
4. Give every slice the same output contract, so the results compare: the full list of files it opened, then public surface with verbatim signatures, literal defaults, comment-versus-code drift, and traps. `agents/scanner.md` is that contract.
5. Track slices as N of M and name the ones not yet done. A missing slice is a known hole; an unstated one is a false claim of completeness.
6. Diff the union of every slice's file list against the real walk before writing anything. That is the only check that catches a directory no slice was pointed at, which is the failure the per-slice counts cannot see.

Concretely: one set of three related libraries came to 988 non-test files. Twenty-two slices covered all of them and produced 58 comment-versus-code contradictions and roughly 250 traps. A sample would have found some of them and reported the rest as clean.

When a directory genuinely stays unexplained, it goes on the excluded list with the reason, where the coverage check reads it and counts it. Recording it as prose instead leaves the same silence the check exists to break, because an unclaimed path and a path nobody mentioned are indistinguishable a month later.

Run the slices in parallel, as many at once as the work allows. This is not an optimization; it is what makes reading every line affordable at all, and a sequential pass over a large codebase is what tempts sampling.

**Every scanning agent proves its own coverage.** A slice report that says "reviewed the auth module" is unusable, because nothing in it distinguishes reading eleven files from reading three. Require each agent to return the file list it actually opened with a count, measured against the file count of its slice, so the two numbers can be compared. A slice whose numbers disagree is rerun, not accepted, and no agent decides for itself that the rest of its files were uninteresting.

**The writer fact-checks the scanner before using the answer.** A slice report is a research lead, not a source. Whatever it asserts, a default, a signature, an event name, a behavior, is confirmed against the file it names before a word of it reaches a page. Agents infer and compress exactly like the writer does, and a wrong claim laundered through a subagent reads more credible than the same claim written directly, which makes it more dangerous rather than less.

## Phase 3: Verify before you claim

Install steps, build commands, and configuration lists are the parts readers rely on most and the parts that rot first. Check them:

- Do the scripts referenced in the README still exist in the manifest?
- Do the documented environment variables match what the code actually reads? Search for every variable access and compare against `.env.example`. Never open the real `.env` to answer this: the code that reads a variable tells you the name, the type and the default, and the live file adds only values you must not have. The same holds for keys, keystores and credentials files, which are never read, never counted, and never quoted.
- Do documented commands still exist? `--help` will tell you.
- Do version requirements in the docs match what the manifest and CI configuration require?
- Do documented endpoints, exports, or events match what the code defines?

Every mismatch is either something to fix in the new docs or something to flag to the user. Keep a list of both.
